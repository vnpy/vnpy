# 《CTA量化通关》系列文章大纲

> 本文档是系列文章的整体写作指导，面向后续执笔的同事。请在动笔前通读全文，动笔时逐篇对照「各篇详细大纲」执行。配图一律按「十一、配图生产规范」标注 A/B/C 三类来源。有疑问先查本文档的「素材与代码锚点」，再向产品团队确认。

---

## 一、系列定位与目标

### 商业目标

配合公司业务推广重点 **VeighNa Fusion**（期货公司采购后提供给其经纪客户的标准版期货量化平台），通过公众号内容吸引更多潜在用户关注并尝试 Fusion。

### 内容目标（写作时的第一优先级）

**每一篇文章必须让读者在量化知识上有实际收获，即使他不使用 Fusion。** 这是软文成立的前提：知识是主菜，产品是餐具。读者判断一篇文章是不是广告，看的是"删掉产品部分后文章还成不成立"——我们要求删掉后依然是一篇合格的量化科普。

### 目标读者画像

- 有期货交易经验（主观交易为主），对量化/程序化感兴趣但没入门；
- 编程能力弱或为零，被"要先学 Python"劝退过；
- 会被"AI 帮你写策略"吸引，但同时对 AI 半信半疑；
- 关心"到底怎么开始"：数据哪来、代码怎么写、回测怎么看、实盘要办什么手续。

### 系列主线（贯穿所有篇目）

**"从一个交易想法到程序化实盘"的完整旅程 + "每一步如何验证、如何不骗自己"的可信度视角。**

这条主线有一个天然优势：Fusion 内置 CTA Agent 的工作流步骤（生成逻辑 → 确认逻辑 → 生成代码 → 代码检查 → 执行回测 → 优化规划 → 执行优化 → 选择参数）本身就是一条标准的量化方法论教学路线。系列按这条路线推进，产品演示自然嵌入，无需硬性插入。

## 二、软文写作总原则

1. **80/20 结构**：每篇约 80% 篇幅讲通用量化知识（工具中立口吻，"无论你用什么平台"），约 20% 篇幅是"这一步在 Fusion 里实际操作长这样"的演示段（仅用第十一节 **C 类** Fusion 实机截图）。演示段集中出现，不要把产品名撒满全文。
2. **产品作为案例载体，不作为论点**：正文论证只依赖量化知识本身；Fusion 只在"落地演示"环节出现。禁止出现"Fusion 比 XX 更好"式的比较句。
3. **不贬低开源版**：统一口径为两条路径——开源版 VeighNa 适合想自己掌控全栈的开发者；Fusion 适合想先跑通流程的交易者。策略代码同为 CTA 模板（`CtaTemplate`），两边互通，用户可以随时进阶。这样既不伤害开源社区读者感情，也给 Fusion 用户"不会被锁死"的安全感。
4. **反"AI 躺赚"叙事**：全系列的差异化人设是"负责任的量化教育者"。反复传递：AI 降低的是实现门槛，不是思考门槛；AI 的输出必须验证（这也与 Fusion 用户协议中"AI 输出需独立审查验证、未经充分验证不得直接实盘"的条款一致，可以正面引用为知识点）。
5. **观念钩子**：每篇设计一句可被单独转发的观点句（详见各篇大纲的「钩子句」），用于文章开头或加粗强调，提升转发率。
6. **篇末固定产品段 + 预告**：见下文「统一产品说明文案」。连载读者第二次看到会自动跳过，不反感；新读者恰好需要。

## 三、文风与格式规范

延续 `article/alpha/outline.md` 为多因子系列定下的公众号规范：

- **单篇不超过 3000 字**（不含代码块与图注）。内容超了就拆知识点到后篇或删，不要放宽。
- 开篇 2～3 段交代背景 + 承接上一篇 + 本篇任务；语气正式、可读，避免口号堆砌。
- `##` / `###` 层级清楚；技术说明多用编号列表或短横线分点。
- 产品名、模块名保留英文（VeighNa Fusion、`CtaTemplate`、`ArrayManager` 等），首次出现紧跟中文解释。
- 术语首次出现给一句话定义（如"主力合约""前复权""未来函数"），后文直呼其名。
- **品类术语口径（全系列统一）**：正文以"CTA量化""CTA量化策略"指代本系列讨论的品类，减少"期货量化""程序化交易"等泛称的使用频率。"期货"一词仅保留在三类场景：机构名称（期货公司）、合约知识本体（合约到期、连续合约等）、监管法规相关表述。CTA 的一句话定义在第 1 篇开篇给出，后篇直接使用。
- **人称口径**：公众号为公司账号，第一人称统一用"我们"（团队/社区视角），不使用单数"我"作者自称；引用读者提问或读者内心独白中的"我"（如"我感觉能赚钱"）不受此限。
- 每篇明确写出"本篇不展开什么"，控制读者预期。
- 篇末：小结（3～5 条要点）+ 下一篇预告（一句话说清下篇解决什么问题）。
- 统一对外链接（按需出现在文末）：官网文档 <https://www.vnpy.com/docs/cn/index.html>、社区论坛 <https://www.vnpy.com/forum/>。

### 统一产品说明文案（每篇文末固定段，克制、不展开）

> VeighNa Fusion 是 VeighNa 团队面向期货公司推出的标准化CTA量化交易平台，由合作期货公司采购后提供给其客户使用。在合作期货公司开户并申请开通相关权限后即可使用，无需额外付费。文中演示均基于 Fusion 内置功能完成。如希望了解详情，可在公众号后台留言咨询。

（最终措辞发布前需与商务/合规确认一次，之后全系列复用，不逐篇改写。）

## 四、合规红线（全系列强制）

1. **禁止任何收益承诺或暗示**：不出现"稳定盈利""跑赢""年化 XX%"等表述；展示回测结果时必须注明"历史回测结果不代表未来表现"。
2. **回测演示数据口径**：所有截图中的回测结果只用于说明"报告怎么读"，不用于证明"策略赚钱"。优先选择结果平庸甚至亏损的案例——这反而强化"验证"主题的可信度。
3. **AI 表述**：不写"AI 自动帮你赚钱"，统一为"AI 辅助策略投研开发"；明确 AI 输出需人工确认与验证（与用户协议一致）。
4. **监管相关内容（第 8 篇重点）**：涉及《期货程序化交易管理办法》、程序化交易报备、系统接入测试等表述，发布前必须过合规审核；"Fusion 免去接入测试环节"的准确口径必须与合作期货公司确认后才能成文，写作时先用占位标注 `【口径待确认】`。
5. **不冒用期货公司名义**：不点名任何具体期货公司，统一说"合作期货公司"。

## 六、各篇详细大纲

### 第 1 篇：想做量化，到底从哪开始

**一句话定位**：给"想做量化但不知道从哪开始"的期货交易者一张全景路线图，顺带预告整个系列。

**读者带走的东西**：知道做程序化交易需要跨过哪几道坎（想法规则化、数据、代码、回测验证、合规实盘），以及每道坎的难度到底在哪。

**钩子句**：做量化的第一道坎不是编程，而是把"我感觉能赚钱"翻译成机器能执行的规则。

**发布标题**：【CTA量化通关1 - 想做量化，到底从哪开始】

**章节展开（约 2500 字）**：

1. **开篇（约 400 字）**：从一个典型场景切入——手动盯盘的交易者错过行情/扛单被套，萌生"让程序帮我执行"的念头；点出"量化不神秘，它就是把纪律交给机器"。
2. **五道坎（约 1200 字，本篇核心）**：本节开头配【配图 B：五道坎路线图收藏卡】（规则 → 数据 → 代码 → 验证 → 实盘；适合转发收藏；源码草稿见第十一节，也可先用 A 类 flowchart 导出再美化）；随后逐条展开，每条 200 字左右，只讲"这道坎是什么、难在哪"，不讲怎么过（留给后篇）：
   - 坎一：把想法变成规则（多数人卡在这，不是卡在代码）；
   - 坎二：搞到能用的数据（期货合约会到期，回测数据没那么简单）；
   - 坎三：把规则变成代码（AI 时代这道坎在快速变矮）；
   - 坎四：验证它真的有效（回测会骗人，这是最容易自欺的一步）;
   - 坎五：合规上实盘（程序化交易有监管要求和接入流程）。
   - 每条结尾用一句话预告"本系列第 X 篇展开"。
3. **工具路径的选择（约 500 字）**：介绍两条路径——自己搭开源工具链（VeighNa 开源版，适合有开发能力者）vs 使用期货公司提供的标准平台（Fusion，适合先跑通流程者），两条路径的差异用对比表格呈现（环境搭建 / 获取方式 / 费用 / 自由度 / 适合人群），中立陈述；本系列演示将基于 Fusion，但知识本身与工具无关。配【配图 C：Fusion 主界面或 CTA Agent 工作流全景】一张。
4. **小结 + 系列预告（约 300 字）**：列出全系列篇目清单，配【配图 B：系列 8 篇目录卡】利于收藏转发，预告第 2 篇。

**Fusion 落点**：仅在第 3 节出现一次 + 【配图 C】一张。**本篇克制是全系列成立的关键，产品露出不得超过此范围。**

**不写什么**：不展开任何单个知识点的细节；不讲收益案例；不做开源版与 Fusion 的功能对比表。

**执行注意**：五道坎的排序就是系列目录，写作时必须与后篇实际内容对齐；若后篇结构调整，本篇需同步修改。

### 第 2 篇：你的交易想法，机器看不懂

**一句话定位**：教读者把主观交易思路拆解成机器可执行的规则，这是量化的第一步，也是 AI 时代人类交易员的核心工作。

**读者带走的东西**：一套"想法 → 规则"的拆解框架（信号周期、入场、出场、仓位、止损五要素），以及一份可以模仿的"策略逻辑说明书"范例。

**钩子句**：AI 时代交易员的核心工作不是写代码，而是确认逻辑。

**发布标题**：【CTA量化通关2 - 你的交易想法，机器看不懂】

**章节展开（约 2800 字）**：

1. **开篇（约 300 字）**：承接第 1 篇"坎一"；用一个反例开场——"均线金叉就买入"看似是规则，实际漏掉了周期、仓位、离场、异常处理，机器无法执行。
2. **规则化五要素框架（约 1000 字，本篇核心方法论）**：节首或节中配【配图 A：规则化五要素 flowchart】（源码见第十一节）。
   - 信号周期：用什么级别的 K 线判断（并解释为什么常用 1 分钟合成 15 分钟——交易所提供的最细公开数据与策略判断周期的关系）；
   - 入场条件：方向判断 + 触发时机分离（趋势过滤器 + 突破触发是经典组合）；
   - 出场条件：止损、止盈、反向信号离场，至少要有一个；
   - 仓位规则：固定手数起步，控制变量；
   - 边界情况：无信号时做什么、方向不明时做什么（"不交易"也是必须写明的规则）。
3. **实例演示（约 900 字）**：使用固定案例——"布林带（周期 20、宽度 1.7）+ Aroon（周期 20）判方向 + ATR（周期 14）1.5 倍移动止损，1 分钟合成 15 分钟，固定 1 手"。先展示交易者的"大白话版"，再逐条翻译成五要素齐备的"逻辑说明书版"，两版对照排版。
   - **注意**：此案例是全系列的贯穿案例（素材锚点见文末），第 4～7 篇继续使用，不得中途更换。
4. **Fusion 演示段（约 400 字 + 【配图 C】2～3 张）**：在 Fusion 的 CTA Agent 中输入大白话想法，展示"生成逻辑"步骤产出的结构化策略逻辑；必含【配图 C：等待你确认】——**强调 Agent 会停下来等人确认逻辑，而不是一路黑箱到底**。可选加【配图 A：生成逻辑→确认 的 stateDiagram】（源码见第十一节）强化同一认知。
5. **小结 + 预告（约 200 字）**：预告第 3 篇——"规则有了，回测之前还有一道很多人栽跟头的坎：数据"。

**不写什么**：不讲代码实现（第 4 篇）；不讨论这个案例策略是否赚钱（第 6 篇会用它的回测结果讲"怎么读报告"）；不展开指标原理（布林带/Aroon/ATR 各给一句话解释加参考链接即可）。

**执行注意**：五要素框架是本系列自创的教学框架，命名和顺序在后篇引用时必须一致。

### 第 3 篇：连续合约没搞对，回测结论靠不住

**一句话定位**：解释期货回测数据特有的"合约到期"问题，讲清指数、前复权、后复权三种连续序列的区别与适用场景。

**读者带走的东西**：明白为什么期货回测不能直接用单个月份合约；能根据用途正确选择连续合约类型；理解"不同软件的主力连续数据对不上"是规则差异而非数据错误。

**钩子句**：你回测用的那根"主力连续"K 线，在真实市场上从来没有存在过。

**发布标题**：【CTA量化通关3 - 连续合约没搞对，回测结论靠不住】

**章节展开（约 2800 字）**：

1. **开篇（约 300 字）**：承接第 2 篇；抛出问题——股票有连续的历史价格，期货合约几个月就到期退市，回测三年用什么数据？
2. **为什么需要连续合约（约 500 字）**：讲清换月缺口问题——新旧主力合约价差导致直接拼接会产生虚假跳空，策略会在换月日"凭空赚/亏"一大笔。配【配图 B：换月拼接跳空示意】（旧合约与新合约价格线 + 缺口标注；非软件 UI）。
3. **三类连续序列（约 900 字，本篇核心）**：
   - 指数合约：多合约按持仓量加权，反映品种整体价格，平滑但不可交易，适合看趋势和做研究；
   - 前复权主力连续：当前价格是真实的，历史价格向后调整（Panama 平移），适合回测（信号价格与当下真实价格一致）；同时如实讲清其特性：长期升水品种的远期历史价格可能逼近零甚至为负，且每次重建后全历史数值会变——这不是 bug，是加法复权的数学特性；
   - 后复权主力连续：历史价格锚定不变，适合做长期净值类分析。
   - 用一个表格汇总三者的"价格真实性 / 适用场景 / 注意事项"。
4. **主力切换规则（约 400 字）**：解释"主力合约"如何认定——商品期货常用"日终持仓量最大且超过原主力 1.1 倍，次日生效"；中金所品种常用"成交量与持仓量双第一，次日生效"；只向更远月滚动。由此引出关键认知：**换月规则和缺口处理方法不同，不同软件生成的主力连续数据必然对不上，这是预期行为**。这一点是市面上极少有人写透的高价值知识点，值得加粗强调。
5. **Fusion 演示段（约 400 字 + 【配图 C】2～3 张）**：数据中心——【配图 C：下载入库】、【配图 C：重建连续合约】、【配图 C：`rb90`/`rb91`/`rb92` 列表】；提醒读者：追加下载新数据后需手动重建连续序列。
6. **小结 + 预告（约 300 字）**：预告第 4 篇——"数据就绪，该让 AI 写代码了，但你得能看懂它写了什么"。

## 九、反「AI 味」写作规范（全系列强制）

读者对 AI 辅助写作的典型痕迹（模板化句式、过度工整的结构、没有真人细节的空洞陈述）反感强烈，且这种反感会直接迁移为对产品的不信任。本系列必须规避。以下配额为硬性要求，纳入第十节验收清单。

### 1. 句式配额（每篇硬性限制）

- "不是 X，而是 Y"及其变体（"并非…而是…""不在于…而在于…"）：全篇不超过 1 处；
- "值得注意的是""需要强调的是""换句话说""综上所述"：禁用；
- "真正的 X""X 的本质""底层逻辑"：全篇不超过 1 处；
- 三项并列排比（"更快、更稳、更省心"式）：全篇不超过 2 处；
- 自问自答句式（"为什么？因为…"）：全篇不超过 2 处；
- 相邻两段不得都以连接词（然而 / 此外 / 同时 / 事实上）开头。

### 2. 排版配额与视觉节奏

反 AI 味限制的是"把论证肢解成要点列表"，公众号阅读体验靠的是另一套视觉手段，两者不冲突。以下前三条是限制，后四条是要求：

- 加粗：全篇不超过 5 处，只留给钩子句和关键认知，不用于普通强调；
- 列表：知识讲解默认用叙述段落；列表仅用于真正可枚举的操作步骤和清单；两个列表之间至少隔一段叙述文字（本条限制针对正文论证，不针对表格、配图和提示框）；
- 不强制每节末尾写小结句，只在篇末统一小结；避免各节长度过分均匀的"对称感"；
- 单个段落不超过 150 字（手机端约 4 行），长段必须拆分——这是提升公众号阅读意愿最有效的手段；
- 每篇配图 3～5 张；来源仅限第十一节三类：**A Mermaid 流程图 / B 多模态生成图 / C Fusion 实机截图**；正文占位统一写成 `【配图 A/B/C：说明】`；
- 对比类内容优先用表格呈现（如路径对比、连续合约类型对比）；
- 金句与注意事项可用引用块（>）独立呈现，作为加粗之外的强调手段；
- **特别提醒**：本大纲文档本身是规格书风格（列表与加粗密集），供执行核对使用，正文写作不得照搬这种排版风格。

### 3. 活人感要求（每篇至少满足两条）

- 使用写作前置任务（第七节）中真实运行产生的细节：具体的报错文本、真实耗时、第一次运行的意外结果、Agent 生成代码里实际发现的问题；
- 至少一处第一人称的真实经历或判断；公众号为公司账号，第一人称统一用"我们"（团队/社区视角），如"我们在论坛里回答过…""我们第一次跑这个案例时…"，不使用单数"我"；
- 用具体数字和具体对象替代模糊量词，删除"某些情况下""很多时候"这类无信息量的表述；
- 允许承认不确定与边界（"这个问题我也没有标准答案"），不必处处周全。

活人感的来源是具体细节和真实判断，而不是语气词。公众号既有文风为正式语体，不必为了去 AI 味刻意口语化，正式而有细节，好过油滑而空洞。

### 4. AI 使用流程约定

- 允许用 AI 做资料核对、事实检查、结构草稿；
- 正文成稿必须人工逐段重写，禁止将 AI 生成段落直接粘贴进正文；
- 发布前做"朗读测试"：执笔人通读全文一遍，读起来不像自己说话的句子必须改。
